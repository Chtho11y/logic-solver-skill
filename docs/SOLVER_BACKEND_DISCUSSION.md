# 讨论：连通性与单回路的编码方式 —— 是否更换求解后端

本文件对应审查结论第 7 项。它**不是**执行计划，而是一份决策材料：问题是什么、有哪几条路、各自代价、需要先测什么、以及需要你拍板的几个问题。

P1–P6 的执行计划见 `docs/DSL_REFACTOR_PLAN.md`。本文件的任何选项都**不阻塞** P1–P6，可以在它们之后再决定。

---

## 1. 问题陈述

四类机制在 z3 的整数算术上属于最差编码方式，而它们恰好是这个项目用得最多的：

### 1.1 同值连通分量：生成树距离见证

`builtins.py:714-753` 的 `_build_value_cc`，以及 `compiler.py:610-648` 的 `_ensure_cc`（CC 变量版），都是同一个套路：

- 每格一个 `id` 整数（等于分量内最小线性下标）
- 每格一个 `dist` 整数
- `(dist == 0) == (id == lin)`
- `Implies(dist > 0, Or(邻居中存在同值、同 id、dist 恰小 1 的))`
- 对每个邻居额外加 `Implies(同值, id 相等)`

这是**用整数算术模拟图算法**。z3 的 QF_LIA 对连通性没有任何特化传播：每次分支后都要靠算术推理重新发现「这块被切断了」。而这件事在专用传播器里是一次并查集或一次 BFS。

覆盖面：`connected` / `connected8` / `cc_count` / `cc_id` / `cc_root` / `cc_*_in` 被涂黑家族几乎全部规则使用，加上所有 CC 变量（分区家族 30 条）。

### 1.2 分量面积/外接框：O(N²) If 求和

`_ensure_cc_size`（`builtins.py:782-794`）给每格一个 size 变量，等于「全盘所有格中 id 与我相同的个数」：

```
sizes[p] == Sum([If(ids[q] == ids[p], 1, 0) for q in cells])
```

9×9 盘面 = 81 × 81 = **6561 个 If 项**。`_ensure_cc_bbox`（`builtins.py:884-908`）更重：每格 4 条 min/max 折叠链，每条链长度 N。

`GRAMMAR.md:482` 自己写了「O(N²) 编码，大盘面谨慎」，但 `place2.dsl` 的所有形状判定都建立在它之上（P4/P6 会缓解一部分，但不改变复杂度）。

### 1.3 单回路：同一套 id + dist

`_link_connect`（`builtins.py:1281-1311`）对 corner 图或 cell 图重复了 1.1 的编码，再由 `_loop_common`（1314）加上度数约束与 `roots == 1`。

覆盖面：`loop` / `cloop` / `connect_edges` / `connect_links` —— 回路 I/II + 路径 I/II 共 **50 条以上**规则的地基。

回路问题的正统解法是 CP 的 `circuit` / `subcircuit` 全局约束，或 SAT + 惰性子环消除。整数 id+dist 是所有可选方案里传播最弱的一种。

### 1.4 从候选集合选不重叠对象

`loops2.dsl:140-219` 的 `rectangular_loops` 及其辅助（`hlink_rect_count` / `vlink_rect_count` / `corner_rect_count` / `on_drawn_rect` / `inside_drawn_count`）：用 `cells() × cells()` 枚举全部 O(N⁴) 个矩形，每个再 O(N) 检查周长，合计 **O(N⁵) 约束项**。

同类：`place2.dsl:199-204` 的 `freely_congruent` 是 O(8N⁴)，`parts_congruent`（239）是 O(8N⁴)。

这类问题在 CP 里是 `diffn` / `geost` / table 约束，在 MILP 里是集合覆盖 + 列生成。**P6 已经计划用「编译期候选枚举 + 精确覆盖」解决其中大部分**，所以 1.4 基本可以在不换后端的前提下消化掉 —— 它列在这里是为了说明「同一批症状里有些不需要换后端」。

## 2. 为什么这是架构决策而不是局部优化

因为 **z3 的 API 直接暴露给了整个内置函数层**。

`ctx.z3` 被传给每一个 builtin（`builtins.py:18` 的文档、`compiler.py:118` 的 `self.z3`），实测调用点：

| 文件 | `z3.` 调用点数 |
|---|---|
| `builtins.py` | **81** |
| `compiler.py` | **26** |
| `solver.py` | 9 |
| 合计 | **116** |

也就是说，DSL 的语义（`If` / `Sum` / `Distinct` / `Implies` / `And` / `Or` / `Int` / `Bool` / `BoolVal`）是**直接写在 z3 词汇表上的**，没有中间层。

后果：
- 换后端 ≠ 换一个 `solve()` 实现，而是要先抽出一层约束构造抽象（约 116 个调用点）。
- 但反过来看，这 116 个调用点用到的 z3 特性其实**很窄**：只有整数/布尔线性算术 + `If` + `Distinct`，没有量词、没有数组、没有 bit-vector、没有 unsat core、没有 optimization。这意味着抽象层本身不难写，难的是回归验证。

**这是本决策的核心事实：迁移成本主要在抽象层与回归验证，而不在语义表达力。**

## 3. 候选方案

### 方案 A：留在 z3，只改编码（单流 / 多商品流）

把「连通」从「树距离见证」改成「网络流」：选一个根，每条边一个流量变量，每个被选格消耗 1 单位，根提供 k 单位。连通 ⟺ 流可行。

- 优点：不换后端，不需要抽象层；流约束是纯线性，z3 的 LIA 对它比对 `dist` 见证友好一些（是真正的线性系统，而非离散跳变）。
- 缺点：变量数从 O(N) 升到 O(边数)，且 z3 没有网络单纯形，仍是通用 LIA 求解。**收益不确定**。
- 判断：这是最便宜的实验（只改 `_build_value_cc` 与 `_link_connect` 两个函数），值得先做，但我不预期它是答案。

### 方案 B：留在 z3，改用惰性连通割（solve → 检查 → 加割 → 重解）

彻底去掉 `id` / `dist` 变量。先只加度数/局部约束求解，拿到模型后在 **Python 里** 跑一次并查集：

- 若已连通 → 接受。
- 若断成 k 块 → 对每一块加一条割子句「这块的边界必须至少有一条被选中/被改变」，然后重解。

- 优点：变量数大幅下降；每次求解都很快；这是 Slitherlink/TSP 类求解器的标准做法（子环消除）。z3 的增量求解（`solver.push/pop` 或直接 `add`）天然支持。
- 缺点：迭代次数不可预测，最坏情况指数级；需要为「连通」「单回路」「无 2×2」等分别设计割，割的强度直接决定收敛速度；实现与调试复杂度显著高于当前。
- 关键优势：**它不需要抽象层，不引入依赖，且可以按 key 灰度开关**（某些规则用惰性割，某些仍用见证编码）。
- 判断：这是「不换后端」路线里唯一可能带来数量级改善的选项。

### 方案 C：换 OR-Tools CP-SAT

- 优点：`AddCircuit` 原生支持单回路（正是 1.3 的答案）；布尔核心 + 惰性子句生成，对 0/1 局部约束（`no2x2` / 邻域计数 / PB）强得多；支持全解枚举（直接解决唯一解判定）；有 `AddAllowedAssignments`（table 约束，服务 1.4 与 P6）。
- 缺点：**重量级三方依赖**。这与项目既有工程惯例冲突 —— `puzzle/server.py` 全程只用 stdlib，z3 本身是**可选**依赖（`solver.py:57-64` 的 `is_available()`、`GRAMMAR.md:404` 的「z3 未安装时返回 STATUS_ERROR」）。CP-SAT 没有对应的「优雅降级」故事。
- 缺点：没有原生的「同值连通分量」约束。`AddCircuit` 解决回路，但涂黑家族的连通性仍需自己编码（不过 CP-SAT 的布尔传播 + 惰性割组合会比 z3 好）。
- 判断：技术上最对症，工程上与项目定位冲突最大。

### 方案 D：换 MiniZinc / Chuffed（外部求解器进程）

- 优点：`circuit` / `subcircuit` / `tree` / `diffn` / `regular` / `global_cardinality` 全部原生（1.1–1.4 全覆盖，外加 `runs` 的 regular 约束，见下）；声明式模型可读性高。
- 缺点：需要外部二进制 + 模型文本生成 + 结果回解析，链路比库调用长得多；错误定位（DSL 行号 → MiniZinc 行号 → 求解器）会退化，而项目在 LSP 诊断上刚投入（见 `docs/LSP_PLAN.md`）；启动开销对小盘面不划算。
- 判断：表达力最匹配，工程链路最长。

### 方案 E：自建专用传播器

为连通性/回路写一个 CDCL(T) 风格的自定义理论求解器。

- 判断：**不建议**。这是一个独立的研究工程，与本项目「实现 236 条谜题规则」的目标不成比例。列出仅为完整性。

## 4. 一个容易被忽略的第五类症状：`runs` 应该用自动机

`_match_slots_to_clues`（`builtins.py:1102-1130`）为每个 (线索, 槽位) 对造一个布尔，再加两组基数约束，规模 K×N。而「0/1 序列的段长模式」是 **regular 约束 / DFA 传播**的教科书场景 —— Nonogram 行约束的标准做法是行内 DP 或自动机传播。

- 在 z3 上：没有 regular 约束，但可以手工把 DFA 展开成「每位置一个状态变量 + 转移约束」（规模 O(N × 状态数)，状态数由线索决定）。这是**不换后端也能做**的改进，且比当前的匹配变量方案传播强得多。
- 覆盖：`nonogram` 及所有用 `runs` / `runs_set` / `runs_cycle` / `row_runs` / `col_runs` 的规则，加上 `cts` 的 `*` 通配（DFA 天然支持通配段 —— 这会**顺带解决** P6 未承诺的 `cts` 缺口）。

**这一项我认为优先级高于换后端**，因为它便宜、局部、且顺带解掉一个已知缺口。它可以作为「P7 候选」独立立项，不涉及架构决策。

## 5. 决策前必须先测什么

现在没有任何性能数据，所以上面所有判断都是基于编码规模的**推断**，不是实测。在做架构决策之前，必须先有以下测量（依赖 `DSL_REFACTOR_PLAN.md` 的 P0 基线）：

| 编号 | 测量 | 用途 |
|---|---|---|
| M1 | 236 条各自的：约束数、辅助变量数、求解耗时、是否超时 | 确认瓶颈是否真的在连通性/回路上，而不是别处 |
| M2 | 按机制归因：关闭 `cc_*` / `loop` / `cloop` 后（用固定答案钉住相应变量）耗时如何变化 | 量化「连通性编码」在总耗时中的占比 |
| M3 | P1（布尔降型）落地后重测 M1 | P1 可能已经吃掉相当一部分开销；若如此，换后端的紧迫性大幅下降 |
| M4 | 盘面规模敏感性：对同一规则用 6×6 / 9×9 / 12×12 / 15×15 测耗时曲线 | 判断是「常数大」还是「复杂度爆」。前者不必换后端，后者必须换 |
| M5 | 方案 A（网络流编码）在 3–5 条代表性规则上的对比实验 | 最便宜的验证，可能直接排除或采纳 A |

**我的建议：先做 P1，再做 M1–M4，然后再回到这份文档。** 因为 P1 是零语义风险的，而且它改变的正是「整数 vs 布尔」这个和后端选择高度相关的维度 —— 在 P1 之前测出的数据，对后端决策没有参考价值。

## 6. 我的倾向

按「收益 / 成本 / 与项目定位的契合度」排序：

1. **第 4 节的 DFA 化 `runs`** —— 便宜、局部、顺带解决 `cts`。不涉及架构决策，建议直接立项。
2. **方案 B（惰性连通割）** —— 不换后端、不加依赖、可按 key 灰度、天花板高。缺点是实现复杂，但复杂度局限在 `builtins.py` 的两三个函数 + `solver.py` 的求解循环。
3. **方案 A（网络流）** —— 作为 M5 实验做掉，成本极低，结果二值：有效就采纳，无效就排除。
4. **方案 C / D** —— 只在 M4 显示「复杂度爆炸、且 B 也救不了」时才考虑。届时需要先付抽象层的成本（116 个调用点）。
5. **方案 E** —— 不做。

另外一条与后端无关但同等重要的事：**唯一解判定目前完全缺失**（`verify.py` 只验样例可满足，`IMPLEMENTATION_STATUS.md:219-220` 已列为已知遗留）。在 z3 上实现方式是「求一个解 → 加入否定该解的约束 → 再求一次 → 期望 UNSAT」，这不需要换后端，属于 P0 的自然延伸。如果项目目标包含**出题器**（而非仅解题器），这一项的优先级应当高于本文件的一切内容 —— 因为 48 条部分实现「作为解题器不漏解，作为出题器会多解」，而现在没有任何手段能自动发现多解。

## 7. 需要你拍板的问题

1. **项目定位**：只做解题器，还是也要做出题器？这决定唯一解判定的优先级，进而决定是否需要「全解枚举」能力（后者强烈倾向 CP-SAT）。
2. **依赖政策**：`z3` 目前是可选依赖，`server.py` 是纯 stdlib。是否允许引入 OR-Tools 这样的重量级依赖？如果不允许，方案 C/D 直接出局，讨论收敛到 A/B + DFA。
3. **性能目标**：现在没有目标值。是「所有规则 60 秒内出解」（`runner.py:30` 的默认 timeout 是 60000ms），还是「典型盘面 5 秒内」？没有目标就无法判断优化是否够了。
4. **盘面规模上限**：是否需要支持 15×15 以上？如果最大只到 12×12，O(N²) 编码可能根本不是问题，1.2 节的担忧就是过度设计。
5. **改动预算与顺序**：是否同意「先 P1 + M1–M4，再回到本文件」的路线？还是希望现在就锁定一个后端方向？

在第 2、3、4 项明确之前，我不建议动 §1.1 与 §1.3 的编码 —— 那是全仓库 200 余条规则的地基，缺乏测量与目标就改它，风险与收益都无法评估。
