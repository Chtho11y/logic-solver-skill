# 讨论：连通性与单回路的编码方式 —— 是否更换求解后端

本文件对应审查结论第 7 项。它**不是**执行计划，而是一份决策材料：问题是什么、有哪几条路、各自代价、需要先测什么、以及需要你拍板的几个问题。

P1–P6 的执行计划见 `docs/DSL_REFACTOR_PLAN.md`。本文件的任何选项都**不阻塞** P1–P6，可以在它们之后再决定。

---

## 1. 问题陈述

四类机制在 z3 的整数算术上属于最差编码方式，而它们恰好是这个项目用得最多的：

### 1.1 同值连通分量：生成树距离见证

`builtins.py:714-753` 的 `_build_value_cc`，以及 `compiler.py:610-648` 的 `_ensure_cc`（CC 变量版），都是同一个套路：

- 每格一个 `id` 整数（等于分量内最小线性下标）
- 每格一个 `dist` 整数
- `(dist == 0) == (id == lin)`
- `Implies(dist > 0, Or(邻居中存在同值、同 id、dist 恰小 1 的))`
- 对每个邻居额外加 `Implies(同值, id 相等)`

这是**用整数算术模拟图算法**。z3 的 QF_LIA 对连通性没有任何特化传播：每次分支后都要靠算术推理重新发现「这块被切断了」。而这件事在专用传播器里是一次并查集或一次 BFS。

覆盖面：`connected` / `connected8` / `cc_count` / `cc_id` / `cc_root` / `cc_*_in` 被涂黑家族几乎全部规则使用，加上所有 CC 变量（分区家族 30 条）。

### 1.2 分量面积/外接框：O(N²) If 求和

`_ensure_cc_size`（`builtins.py:782-794`）给每格一个 size 变量，等于「全盘所有格中 id 与我相同的个数」：

```
sizes[p] == Sum([If(ids[q] == ids[p], 1, 0) for q in cells])
```

9×9 盘面 = 81 × 81 = **6561 个 If 项**。`_ensure_cc_bbox`（`builtins.py:884-908`）更重：每格 4 条 min/max 折叠链，每条链长度 N。

`GRAMMAR.md:482` 自己写了「O(N²) 编码，大盘面谨慎」，但 `place2.dsl` 的所有形状判定都建立在它之上（P4/P6 会缓解一部分，但不改变复杂度）。

### 1.3 单回路：同一套 id + dist

`_link_connect`（`builtins.py:1281-1311`）对 corner 图或 cell 图重复了 1.1 的编码，再由 `_loop_common`（1314）加上度数约束与 `roots == 1`。

覆盖面：`loop` / `cloop` / `connect_edges` / `connect_links` —— 回路 I/II + 路径 I/II 共 **50 条以上**规则的地基。

回路问题的正统解法是 CP 的 `circuit` / `subcircuit` 全局约束，或 SAT + 惰性子环消除。整数 id+dist 是所有可选方案里传播最弱的一种。

### 1.4 从候选集合选不重叠对象

`loops2.dsl:140-219` 的 `rectangular_loops` 及其辅助（`hlink_rect_count` / `vlink_rect_count` / `corner_rect_count` / `on_drawn_rect` / `inside_drawn_count`）：用 `cells() × cells()` 枚举全部 O(N⁴) 个矩形，每个再 O(N) 检查周长，合计 **O(N⁵) 约束项**。

同类：`place2.dsl:199-204` 的 `freely_congruent` 是 O(8N⁴)，`parts_congruent`（239）是 O(8N⁴)。

这类问题在 CP 里是 `diffn` / `geost` / table 约束，在 MILP 里是集合覆盖 + 列生成。**P6 已经计划用「编译期候选枚举 + 精确覆盖」解决其中大部分**，所以 1.4 基本可以在不换后端的前提下消化掉 —— 它列在这里是为了说明「同一批症状里有些不需要换后端」。

## 2. 为什么这是架构决策而不是局部优化

因为 **z3 的 API 直接暴露给了整个内置函数层**。

`ctx.z3` 被传给每一个 builtin（`builtins.py:18` 的文档、`compiler.py:118` 的 `self.z3`），实测调用点：

| 文件 | `z3.` 调用点数 |
|---|---|
| `builtins.py` | **81** |
| `compiler.py` | **26** |
| `solver.py` | 9 |
| 合计 | **116** |

也就是说，DSL 的语义（`If` / `Sum` / `Distinct` / `Implies` / `And` / `Or` / `Int` / `Bool` / `BoolVal`）是**直接写在 z3 词汇表上的**，没有中间层。

后果：
- 换后端 ≠ 换一个 `solve()` 实现，而是要先抽出一层约束构造抽象（约 116 个调用点）。
- 但反过来看，这 116 个调用点用到的 z3 特性其实**很窄**：只有整数/布尔线性算术 + `If` + `Distinct`，没有量词、没有数组、没有 bit-vector、没有 unsat core、没有 optimization。这意味着抽象层本身不难写，难的是回归验证。

**这是本决策的核心事实：迁移成本主要在抽象层与回归验证，而不在语义表达力。**

### 2.1 关键设计：双层 IR

如果将来要抽象，**必须分两层**，否则抽象层没有价值：

```
L1  表达式层：Term(sort) + And/Or/Not/Implies/If/Sum/Distinct/算术比较
              所有后端必须支持。约 100 个调用点是机械替换。

L2  全局约束层：声明式意图节点
              Connected(cells, mask, kind)      -- 连通性
              Circuit(arcs)                     -- 单回路
              RunLengths(seq, clues, ordered)   -- 段长模式
              Table(vars, tuples)               -- 外延约束
              Cardinality(vars, value, count)   -- 计数
              NoOverlap(placements)             -- 不重叠放置
```

L2 节点的处理规则：**后端原生支持就直接用，不支持就降级展开成 L1。**

关键洞察：**这些降级实现就是现在的 `_build_value_cc` / `_link_connect` / `_match_slots_to_clues` / `_fn_runs` / `_fn_drop_covers` / `_ensure_cc_bbox`，不需要重写，只是搬家。**

为什么必须有 L2：116 个调用点里约 100 个是机械替换，但上面这 6 个函数是**编码算法**而非表达式。如果抽象层只有 L1，这些算法会原样保留，所有后端拿到同样（低效）的编码 —— 换后端就只剩「求解引擎差异」，拿不到 `AddCircuit` / `global_cardinality` / `regular` 的好处，也就失去了换后端的主要理由。

四个好处：
1. 现有算法零重写，变成「z3 后端的降级实现」。
2. 新后端只实现它擅长的 L2 节点，其余自动降级 → **增量迁移，不是全或全无**。
3. **§1.1 的「树距离 vs 费用流」自动消解**：`Connected` 是意图节点，编码选择变成 z3 后端**内部**的策略，DSL 层不需要任何开关。
4. L2 节点可分析：编译期能统计「本规则用了哪些全局约束」，从而自动建议后端。

### 2.2 前提：必须先做 API 分层

L2 抽象的前提是「DSL 只表达意图，不接触编码」。而现在 `cc_id` / `cc_root` / **CC 变量的 id 语义**是赤裸的编码泄漏，被 **47 条规则**依赖（10 个 `cc_id` + 2 个 `cc_root` + 35 个 CC 变量）。只要泄漏还在，`Connected` 就不能是纯意图节点，L2 抽象是漏的。

**顺序：API 分层（已立项为 `DSL_REFACTOR_PLAN.md` 的 P4A）→ L2 IR → 多后端。反过来做会失败。**

### 2.3 现在的建议：不实施，但现在就画边界

在做 P3–P6 的新增内置时，就按「意图节点」的形状设计签名 —— P5 的 `orient` 天然是 `Circuit`，P6 的 `place_shapes` 天然是 `NoOverlap`。这样抽象层将来是**长出来的**而不是**重构出来的**。这个成本为零。

## 3. 候选方案

### 方案 A：留在 z3，只改编码（单流 / 多商品流）

把「连通」从「树距离见证」改成「网络流」：选一个根，每条边一个流量变量，每个被选格消耗 1 单位，根提供 k 单位。连通 ⟺ 流可行。

- 优点：不换后端，不需要抽象层；流约束是纯线性，z3 的 LIA 对它比对 `dist` 见证友好一些（是真正的线性系统，而非离散跳变）。
- 副产品：**L4（分量面积）用流反而优于现状** —— 单流中根的供给量恒等于分量大小，是流量守恒的直接产物，O(边数) 变量；而 `_ensure_cc_size` 是 6561 个 `If`（9×9）。但要读「任意格所在分量的面积」还需沿流反向传播一个值，这部分不免费。
- 缺点：变量数从 O(N) 升到 O(边数)，且 z3 没有网络单纯形，仍是通用 LIA 求解。**收益不确定**。
- **硬性限制**：费用流的自然产物是「边流量 + 节点被哪个根覆盖」，**不产生 canonical id**。而 `META_SOLVE_PLAN.md` §4.4 要求 L3/L5 必须保持 canonical id（否则唯一性判定误报多解）。**因此方案 A 只能用于不暴露 id 的 L1 层。**
- 判断：这是最便宜的实验（只改 `_build_value_cc` 的 L1 路径），值得先做，但我不预期它是答案。

### 方案 B：留在 z3，改用惰性连通割（solve → 检查 → 加割 → 重解）

彻底去掉 `id` / `dist` 变量。先只加度数/局部约束求解，拿到模型后在 **Python 里** 跑一次并查集：

- 若已连通 → 接受。
- 若断成 k 块 → 对每一块加一条割子句「这块的边界必须至少有一条被选中/被改变」，然后重解。

- 优点：变量数大幅下降；每次求解都很快；这是 Slitherlink/TSP 类求解器的标准做法（子环消除）。z3 的增量求解（`solver.push/pop` 或直接 `add`）天然支持。
- **与 PM 共享基础设施**：`META_SOLVE_PLAN.md` 的 PM-0 已经要引入持久 session + `push`/`pop` + flush 游标，而惰性割需要的正是这套东西。**PM 落地后方案 B 的实现成本显著下降** —— 这是把 PM 排在前面的额外收益。
- 缺点：迭代次数不可预测，最坏情况指数级；需要为「连通」「单回路」「无 2×2」等分别设计割，割的强度直接决定收敛速度；实现与调试复杂度显著高于当前。
- 关键优势：**它不需要抽象层，不引入依赖，且可以按 key 灰度开关**（某些规则用惰性割，某些仍用见证编码）。
- 判断：这是「不换后端」路线里唯一可能带来数量级改善的选项。

### 方案 C：换 OR-Tools CP-SAT

**体积**（实测发布数据）：wheel 23.9 MB (win_amd64) / 29.8 MB (manylinux x86_64) / 21.9 MB (macosx arm64)；安装后约 100–150 MB（含 protobuf、abseil、SCIP、GLOP）。对比基准：本机 z3 安装后 **20.4 MB**（`C:\Python314\Lib\site-packages\z3`）。即**安装后约为 z3 的 5–7 倍**，且引入 protobuf 传递依赖。

- 优点：`AddCircuit` 原生支持单回路（正是 1.3 的答案）；布尔核心 + 惰性子句生成，对 0/1 局部约束（`no2x2` / 邻域计数 / PB）强得多；支持全解枚举（直接解决唯一解判定）；有 `AddAllowedAssignments`（table 约束，服务 1.4 与 P6）。
- 缺点：**重量级三方依赖**。这与项目既有工程惯例冲突 —— `puzzle/server.py` 全程只用 stdlib，z3 本身是**可选**依赖（`solver.py:57-64` 的 `is_available()`、`GRAMMAR.md:404` 的「z3 未安装时返回 STATUS_ERROR」）。CP-SAT 没有对应的「优雅降级」故事。
- 缺点：没有原生的「同值连通分量」约束。`AddCircuit` 解决回路，但涂黑家族的连通性仍需自己编码（不过 CP-SAT 的布尔传播 + 惰性割组合会比 z3 好）。
- **缺点（新增，权重很高）：增量求解支持弱。** 每次 solve 基本要重建 model，只有 solution hint 能传递少量信息。这与 `META_SOLVE_PLAN.md` 的元求解范式（尤其 §8.2 的嵌套枚举）直接冲突。
- 判断：技术上最对症，工程上与项目定位冲突最大；**元求解需求进一步降低了它的吸引力**。

### 方案 D：换 MiniZinc / Chuffed（外部求解器进程）

**体积**（MiniZinc 2.10.0 bundle 实测）：33.5 MB (Windows installer) / 71.5 MB (Linux AppImage) / 77.5 MB (Linux tgz) / 90.1 MB (macOS dmg)，含 IDE + Gecode + Chuffed + COIN-BC。Chuffed 单独约几 MB 但无官方 wheel，需自行编译。

- 优点：`circuit` / `subcircuit` / `tree` / `diffn` / `regular` / `global_cardinality` 全部原生（1.1–1.4 全覆盖，外加 `runs` 的 regular 约束，见 §4）；声明式模型可读性高。
- 缺点：需要外部二进制 + 模型文本生成 + 结果回解析，链路比库调用长得多；错误定位（DSL 行号 → MiniZinc 行号 → 求解器）会退化，而项目在 LSP 诊断上刚投入（见 `docs/LSP_PLAN.md`）；启动开销对小盘面不划算。
- **缺点（新增，权重很高）：无增量求解**（外部进程）。`META_SOLVE_PLAN.md` §8.2 的枚举要付 n 次进程启动 + n 次模型文本生成/解析。
- 判断：表达力最匹配，工程链路最长；**元求解需求基本排除了它**。

### 方案 E：自建专用传播器

为连通性/回路写一个 CDCL(T) 风格的自定义理论求解器。

- 判断：**不建议**。这是一个独立的研究工程，与本项目「实现 236 条谜题规则」的目标不成比例。列出仅为完整性。

### 体积汇总

| 依赖 | 分发包 | 安装后 |
|---|---|---|
| **z3-solver**（现有） | ~20 MB wheel | **20.4 MB**（本机实测） |
| OR-Tools CP-SAT | 21.9–29.8 MB wheel | 约 100–150 MB |
| MiniZinc bundle | 33.5–90.1 MB | 同量级 |
| Chuffed（单独） | 几 MB（需自编译） | — |

结论：**「重量级依赖」的实际成本主要是安装后体积（约 5–7 倍）与传递依赖，而非下载量。** MiniZinc 的真正成本不是体积而是进程链路。

## 4. 一个容易被忽略的第五类症状：`runs` 应该用自动机

`_match_slots_to_clues`（`builtins.py:1102-1130`）为每个 (线索, 槽位) 对造一个布尔，再加两组基数约束，规模 K×N。而「0/1 序列的段长模式」是 **regular 约束 / DFA 传播**的教科书场景 —— Nonogram 行约束的标准做法是行内 DP 或自动机传播。

- 在 z3 上：没有 regular 约束，但可以手工把 DFA 展开成「每位置一个状态变量 + 转移约束」（规模 O(N × 状态数)，状态数由线索决定）。这是**不换后端也能做**的改进，且比当前的匹配变量方案传播强得多。
- 覆盖：`nonogram` 及所有用 `runs` / `runs_set` / `runs_cycle` / `row_runs` / `col_runs` 的规则，加上 `cts` 的 `*` 通配（DFA 天然支持通配段 —— 这会**顺带解决** P6 未承诺的 `cts` 缺口）。

**这一项我认为优先级高于换后端**，因为它便宜、局部、且顺带解掉一个已知缺口。它可以作为「P7 候选」独立立项，不涉及架构决策。

## 5. 决策前必须先测什么

现在没有任何性能数据，所以上面所有判断都是基于编码规模的**推断**，不是实测。在做架构决策之前，必须先有以下测量（依赖 `DSL_REFACTOR_PLAN.md` 的 P0 基线）：

| 编号 | 测量 | 用途 |
|---|---|---|
| M1 | 236 条各自的：约束数、辅助变量数、求解耗时、是否超时 | 确认瓶颈是否真的在连通性/回路上，而不是别处 |
| M2 | 按机制归因：关闭 `cc_*` / `loop` / `cloop` 后（用固定答案钉住相应变量）耗时如何变化 | 量化「连通性编码」在总耗时中的占比 |
| M3 | P1（布尔降型）落地后重测 M1 | P1 可能已经吃掉相当一部分开销；若如此，换后端的紧迫性大幅下降 |
| M4 | 盘面规模敏感性：对同一规则用 6×6 / 9×9 / 12×12 / 15×15 测耗时曲线 | 判断是「常数大」还是「复杂度爆」。前者不必换后端，后者必须换 |
| M5 | 方案 A（网络流编码）在 3–5 条代表性规则上的对比实验 | 最便宜的验证，可能直接排除或采纳 A |

**我的建议：先做 P1，再做 M1–M4，然后再回到这份文档。** 因为 P1 是零语义风险的，而且它改变的正是「整数 vs 布尔」这个和后端选择高度相关的维度 —— 在 P1 之前测出的数据，对后端决策没有参考价值。

## 6. 我的倾向

按「收益 / 成本 / 与项目定位的契合度」排序：

1. **第 4 节的 DFA 化 `runs`** —— 便宜、局部、顺带解决 `cts`。不涉及架构决策，建议直接立项。
2. **方案 B（惰性连通割）** —— 不换后端、不加依赖、可按 key 灰度、天花板高。缺点是实现复杂，但复杂度局限在 `builtins.py` 的两三个函数 + `solver.py` 的求解循环。**且 PM 落地后它与元求解共享持久 session + push/pop 基础设施，实现成本显著下降。**
3. **方案 A（网络流）** —— 作为 M5 实验做掉，成本极低，结果二值：有效就采纳，无效就排除。**注意它只能用于 L1 层**（canonical id 约束，见 §3 方案 A）。
4. **方案 C / D** —— 只在 M4 显示「复杂度爆炸、且 B 也救不了」时才考虑。届时需要先付抽象层的成本（116 个调用点 + L2 节点设计）。
5. **方案 E** —— 不做。

### 6.1 已收敛的部分（原第 7 节问题 1、2 的答案）

用户已明确要求支持元编程范式（编译期 `solve()`、据结果加约束、多解判定、唯一化见证）。这**隐含确定了项目定位包含出题器**，并直接改变结论：

**增量求解（`push`/`pop` + 跨 `check()` 复用学习子句）是 SMT 求解器的天生强项，恰恰是 CP-SAT 与 MiniZinc/Chuffed 的弱项：**

| 后端 | 增量支持 | 对元求解的适配 |
|---|---|---|
| **z3**（现有） | 原生 `push`/`pop`，跨 check 复用 lemma | 完全适配，正是为交互式使用设计 |
| CP-SAT | 弱；每次 solve 基本重建 model | 嵌套枚举代价高 |
| MiniZinc / Chuffed | 无（外部进程） | 需付 n 次进程启动 + n 次文本生成/解析 |

**因此：讨论收敛到「留在 z3 + L2 全局约束抽象 + 惰性割 + DFA 化 runs」。方案 C/D 暂时出局**，除非 M4 显示复杂度爆炸且 B 无法挽救。

唯一解判定已独立立项为 **PM**（`docs/META_SOLVE_PLAN.md`），排在 P1 之后、P2 之前 —— 它不需要换后端，且是 P2–P6 全部改写工作的验收工具。

## 7. 需要你拍板的问题

问题 1、2 已由「元编程需求」隐含回答（见 §6.1）：定位包含出题器 → z3 的增量求解是刚需 → C/D 出局，依赖政策问题暂时无需回答。

**剩余待定：**

1. **性能目标**：现在没有目标值。是「所有规则 60 秒内出解」（`runner.py:30` 的默认 timeout 是 60000ms），还是「典型盘面 5 秒内」？没有目标就无法判断优化是否够了。
2. **盘面规模上限**：是否需要支持 15×15 以上？如果最大只到 12×12，O(N²) 编码可能根本不是问题，§1.2 的担忧就是过度设计。
3. **元求解的性能预算**：`META_SOLVE_PLAN.md` §5.5 需要定两个值 —— `meta:` 块总时间预算（建议 300000ms）与 solve 调用次数上限（建议 200）。这直接决定 §8.2 的唯一化见证枚举能跑多大的盘面。
4. **DFA 化 `runs` 是否立项**（§4）。它独立于后端决策，我建议做，但需要你确认优先级 —— 它会与 P2/P3 竞争工期。

在第 1、2 项明确之前，我不建议动 §1.1 与 §1.3 的编码 —— 那是全仓库 200 余条规则的地基，缺乏测量与目标就改它，风险与收益都无法评估。而 §1.4（不重叠对象选择）已由 `DSL_REFACTOR_PLAN.md` 的 P6 用「编译期候选枚举 + 精确覆盖」消化，不需要换后端。
